# AccelProof 本地提交包 Review 与修改清单

审查对象：`AccelProof-本地提交包.zip`。审查日期：2026-09-28。

## 结论

保留选题、现有前端和受限执行架构，不建议推倒重做。当前包已经具有源码、四类运行记录、独立验证、性能原始样本、工作流导出、报告、征文和视频，超过了仅能点击的原型阶段。但尚不适合作为无需修改的最终交付版本。

优先级最高的不是美化，而是把“验证了什么”“交付了什么”“实际执行哪种后端”严格对应起来。其次，要提高 Agent 与 Skills 的实际决策价值，避免评审将项目理解为固定聚合脚本外加 JSON 参数选择器。

本清单中的“必须修复”是定版建议，不是官方评分或安全漏洞等级。

## 审查方法与限制

检查了 ZIP 目录、源码、最终及部分开发运行记录、官方/自研 Skills、测试与复用脚本、9 页项目报告、2 页征文、离线前端以及视频元数据和代表性画面。对可在当前环境执行的导出逻辑、服务端状态处理和前端状态处理进行了隔离复现。

独立检查结果：外层清单列出的 1544 个文件无哈希不符；工作流内清单列出的 100 个文件无哈希不符；所检查的性能中位数和加速比可由包内样本算出；视频为 232.741 秒，1920×1080，含音频轨。26 个非上游 Python 文件的语法解析未发现错误。

这些检查不等于独立复跑了 GPU 实验。当前审查环境没有所需 GPU，且缺少 pyarrow，依赖补充也因网络解析失败未完成，因此未独立运行原项目完整测试套件、GPU 任务或模型推理。报告中的 GPU 数值均明确视为提交包提供的记录。前端活动任务复现使用模拟 RUNNING API 响应，不是实际启动 GPU。

以下源码路径默认相对 `AccelProof/project/`；报告、文章和视频路径相对 `AccelProof/`。ZIP 内文档没有可用的逐文件检索引用标记，因此以实际文件路径、函数名和行号定位，不把训练课件引用冒充新包证据。

## 已完成且应保留的部分

四配置性能对照区分原始 pandas、原始 cudf.pandas、同构优化 pandas 与同构优化 cuDF；报告也区别了 12.397× 的同构收益和 36.115× 的整体收益。不要删去同构 CPU 对照来换取更大的数字。

故障注入、真实修复、失败不测速、小数据 KEEP_CPU、合成数据和 RTX 4090 实测范围均有明确说明。不能因此将当前受限实现指责为伪造代码生成或伪造现场失败；但界面应进一步直观体现该边界。

上游版本固定、签名文件保留及“不宣称已经做密码学签名验证/官方认证”的表述应保留。当前本地单用户、固定审计模板的安全范围也不应临时扩张为任意 Python 执行服务。

## 必须修复

### R01：验证后的候选策略可以变化，而导出仍保留通过结论

**证据：** `accelproof/harness.py:106–124`。导出检查终态、全量结果、契约与 `protected.json` 中的源码哈希，却没有把准备导出的 `candidate-policy.json` 与验证时使用的内容绑定。导出 manifest 记录的是导出时的当前文件哈希，不是验证时的候选身份。

**独立复现：** 在临时目录复制 `final-large` 的通过记录，将候选策略的 `ttft_policy` 从 `exclude_missing` 改成 `fill_zero`，调用原始 `export_run(..., approved=True)`。函数接受并生成 ZIP；归档中的策略是 `fill_zero`，归档中的原始 run 记录仍是 `exclude_missing`，manifest 的状态仍为 `VERIFIED_GAIN`。

这不是声称存在远程入侵能力。普通的验证后误编辑就足以导致“已验证”标签与实际代码行为不一致，直接影响项目最核心的交付保证。

**修改：** 在验证时保存不可变候选快照，绑定策略、模板、统计契约、验证器/测试、输入和环境身份。输出一份只由控制器写入的验证记录，包含候选摘要和结果摘要。导出只能从该快照生成；当前内容不同则拒绝并要求重验。不要仅把“当前文件”重新算一次哈希。对本地文件的哈希绑定可以防意外修改，但不要扩张为对有权重写整个证据目录的攻击者提供真实性保证。

**验收：** 原样候选可导出；验证后改策略、模板、契约或判卷规则均拒绝；导出包中的候选摘要必须与验证记录相同。无需重新跑大数据即可先补这组门禁回归测试。

### R02：KEEP_CPU 只影响 manifest，复用脚本仍然强制执行 GPU

**证据：** `accelproof/harness.py:121` 按结论生成 `recommended_backend`；`scripts/replay_workflow.py:17–21` 无条件运行 `original_cpu` 和 `optimized_gpu`，并无条件调用 `nvidia-smi`。该脚本没有消费 `recommended_backend`。

**影响：** 小数据虽然显示“保留 CPU”，导出后的执行并未保留 CPU。没有 GPU 的环境也无法沿该路径使用 CPU 工作流。

**修改：** 区分“结果交叉核验命令”和“日常执行命令”。前者可以明确要求 CPU/GPU 双路，后者必须按照已审核的后端选择执行。建议分别提供 `verify` 和 `run` 子命令；CPU 执行路径不应导入 cuDF、不应要求 `nvidia-smi` 或 GPU 锁。复用新规模数据时，还需检查原性能适用范围，而不能只因 schema 相同永久沿用 GPU 推荐。

**验收：** 导出 KEEP_CPU 案例，模拟 GPU 不可用并执行日常 run，CPU 分支成功；记录包含 `selected_backend=cpu`，没有调用 GPU worker。双路复核则必须明确显示为额外验证操作。

### R03：预热后性能收益与实际运行模式没有进入统一决策

**证据：** `accelproof/validation.py:37–44` 只使用各配置的预热后 samples；`accelproof/harness.py:121` 将 `VERIFIED_GAIN` 直接映射成 GPU 推荐。包内 `evidence/cold-summary.json` 的单次新进程观测为：同构 CPU 1.6788 秒，GPU 19.1178 秒。`AccelProof-项目报告.md:76–84` 已诚实解释该边界，README 第 35 行也建议一次性任务优先 CPU。

| 包内计时口径 | 同构 CPU | 优化 GPU | 可支持的表述 |
| --- | ---: | ---: | --- |
| 预热后的单次端到端中位数 | 1.06057 秒 | 0.08555 秒 | 该输入、该节点上的预热后收益约 12.40× |
| 单次新进程总墙钟 | 1.67882 秒 | 19.11778 秒 | 该次观察中 CPU 更快；各一次，不是普遍统计结论 |

**影响：** 说明书区分了口径，程序却没有真正选择运行模式；而当前复用脚本又启动新进程。不能只在 12.40× 旁增加免责声明。

**修改：** 将结果一致性、性能测量结果和部署建议分开。例如保留 `validation_status=PASS`、`warm_speedup=12.40`，另记录 `execution_profile=one_shot|persistent_batch` 和 `recommended_backend`。一次性模式依据新进程端到端测量作决定；常驻模式才依据预热后样本。没有常驻实现时，不把“将来可以摊薄初始化”当作已经交付的性能。

常驻版本应在一个持续存活的 worker 中处理多份输入，并报告初始化与总批次时间；不同输入不能简单重复读取同一小结果。可用 `T_total(N)=T_init+ΣT_i` 组织实验，但不要从这两个不同口径的观测直接编造确定的盈亏平衡次数。

**验收：** 同一工作流选择 one-shot 或 persistent-batch，界面、manifest、实际 worker 及报告口径一致；缺少相应模式的测量就显示未验证，而不是默认推荐 GPU。

### R04：导出工作流与它自带的 README 不一致，干净环境复现不足

**证据一：** `accelproof/harness.py:114–119` 导出源码、Skills、测试、vendor、scripts、requirements.txt 和完整项目 README，却没有导出 `web/`。该 README 第 17 行仍要求启动 Web 服务。独立解压工作流后导入 `accelproof.server`，实际得到 `RuntimeError: Directory '.../web' does not exist`。这与缺少 GPU 无关。

**证据二：** `requirements-lock.txt` 大量依赖为 `file:///dev/shm/accelproof-wheels-20260928/...whl`，这些路径属于原节点，不是可以直接在其他机器安装的锁文件。报告第 145 行却将其作为环境配置步骤。模型运行环境依赖另一个 torch/transformers 环境，README 只给占位路径。导出 ZIP 中也没有项目根 LICENSE 或 requirements-lock.txt。

**修改：** 明确区分完整项目包与精简工作流包。精简包需要自己的 README、真实可运行入口、可移植依赖说明和许可材料；不支持 Web 就删除 Web 命令，支持 Web 就包含所需文件。保留节点环境快照作为证据，但另提供版本/哈希可安装的依赖锁定及独立模型环境安装步骤。将原节点 tmpfs 恢复脚本明确归为节点专用工具。

没有根 `SKILL.md` 不会使现有 Python ZIP 本身失效，但它说明该包目前不是一个可直接安装的单一 Skill。若要称作可直接安装 Skill，应补入口与实际操作说明；否则准确称作“可复现项目工作流包”。

**验收：** 在不含原项目目录、旧 wheel 缓存和旧虚拟环境的临时目录中，按包内自己的 README 完成入口检查。可先完成无 GPU 的 import、help 和 CPU-only 测试，GPU 环境验收另行记录。完整项目 LICENSE 已存在，不要误称整个项目没有许可。

## 稳定性与前端一致性

### R05：终态保存过早，SSE 可能在真正收尾前结束

**证据：** `accelproof/harness.py:98–105` 先把 status 设为最终 verdict，再发布 profile 事件并运行 profiler、核对保护文件、记录 decision/finalize。`accelproof/server.py:55–62` 只要发现 status 不再是 RUNNING 就发送 done 并终止流。`web/app.js:19,21` 据此开启导出按钮和结束监听。

**影响：** 前端可能显示已完成、允许发起导出，而后台还在做最终检查；导出门禁此时通常会拒绝，因为 protected_unchanged 尚未设置。若后续失败，已断开的界面还可能停留在成功状态。

**修改：** verdict 先存成暂定测量结论；状态继续为 RUNNING/FINALIZING。完成 profiler、完整性检查与产物写入后一次性提交终态和 finished；SSE 以该最终提交结束。可选 profiler 失败应是 warning 还是终态失败，需要事先明确。

**验收：** 人为延长/失败 profiler 时，前端不提前 done，不提前开放有效导出；最终错误可被前端收到。不要仅增加前端等待计时器。

### R06：API 重启后可能留下无法恢复的 RUNNING 记录

**证据：** `accelproof/server.py:9,24–28,64–71` 的 jobs 只保存在当前进程内，sync_status 只处理“id 仍在 jobs”这一条件。临时构造磁盘上 RUNNING、当前 jobs 为空的情形，原函数返回 RUNNING 不变；cancel 又要求当前进程拥有该 job。

**修改：** 在启动时协调恢复运行记录。最小实现可以在不能验证进程存活/身份时标记 INTERRUPTED；较完整实现保存进程组、启动身份和心跳，确认后恢复监管。PID 存在本身不能证明是原任务。将活动任务判定持久化，避免重启后同时调度或无法取消。

**验收：** API 重启/异常退出后没有无限 RUNNING；用户能明确知道任务仍在执行、已中断，还是需要恢复。未确认旧进程已结束时不直接另开一个 GPU 作业。

### R07：运行中切换案例会丢失当前任务与取消入口

**证据：** `web/app.js:14,21,24`。实际执行原前端 JS、提供模拟 RUNNING 响应后，切换场景将 current 清空、关闭事件源、界面设 READY，同时启动按钮恢复可点、取消按钮隐藏，后台任务状态仍为 RUNNING。

**修改：** 最小补丁是运行时禁用场景选择；更完整方案区分 activeRun 与 viewedRun，浏览历史不影响活动任务横幅和取消入口。异步事件回调应检查 run_id，避免旧请求覆盖新页面；事件源回调引用自己的连接对象，而非共享可被替换的全局 source。

**验收：** 运行中切换案例或查看历史，不会产生“后台有任务、前端认为未运行”；取消始终作用于显示出来的正确活动任务。

### R08：当前源码差异不等于具体运行的候选/修复差异

**证据：** `accelproof/server.py:89–92` 的 `/api/code` 没有 run_id，只读取当前工作目录 pipeline.py，并对 original 与 optimized 做 diff；`web/app.js:33` 只在初始化获取一次。实际模型输出则是策略，故障与修复改变的是 candidate-policy.json。

**影响：** 不同运行/修复前后看到的代码差异相同。源码更新后，历史记录还可能显示新版实现，不再是该次被测版本。当前文档已说明审计模板，这不是应当指控为伪造模型写代码；问题是运行历史展示与实际变更没有对应。

**修改：** 把“人工审计模板差异”与“本次模型策略差异”分开。增加按 run_id/attempt 获取快照的接口，展示 fill_zero → exclude_missing、preserve_null_keys 和后端决策变化；必要时显示模板参数化后的实际执行版本。修复页直接展示期望值 10、错误值 5、具体规则和复验状态。

**验收：** 不同 attempt 能看到各自策略；更新当前源码不改变旧运行快照；导出使用的候选可从同一页定位。

## Agent / Skills：提高竞争力，不扩大失控范围

### R09：四个 Skills 的可执行入口没有体现各自职责

**证据：** 四个 `skills/*/scripts/run.py:1–2` 内容完全相同，均运行 `accelproof.harness`；例如 `skills/publish-validated-workflow/SKILL.md:11–12` 的命令仍然是 `python -m accelproof.harness --scenario standard`。这会发起整条迁移流程，不是对指定已验证任务进行发布。

**修改：** 二选一：保留一个真正完整的端到端业务 Skill，将四阶段作为内部流程；或者提供明确的阶段 CLI，如 intake、migrate --run-id、validate --run-id、export --run-id --approved。不要为了技能数量保持四份名字不同、执行入口相同的壳。

`accelproof/model.py:23–25` 当前是一次性读取官方与全部自研 SKILL.md，不是按需路由。可保留这种简化，但不要宣传已经实现动态技能发现或渐进加载。选择按阶段只加载相关技能后，重新测评效果及 token 成本。

**验收：** 独立调用导出 Skill 只审核并导出已有运行，不再次生成数据、推理和测速；缺少 run_id 或审批时先澄清/拒绝。无关问题不调用 GPU 任务。

### R10：Agent 的有效决策空间偏小，容易被固定规则替代

**证据：** `accelproof/model.py:6–12` 只有四字段封闭策略；`accelproof/pipeline.py:19–32` 的正确聚合路径由审计模板预先写好。对于当前冻结契约，保留空键与不填零都已有唯一正确答案；最终后端由基准判定，模型的 backend 不是实际执行依据。报告已经披露这一点。

**评审风险：** “既然正确策略已由契约写死，为什么需要一次本地 LLM 推理，而不是几十行确定规则？”这是当前最重要的差异化问题，并不要求改成任意代码执行。

**最低成本增强：** 引入少量都保持正确统计语义、但性能适用条件不同的受审计候选，模型依据数据规模、分组基数、运行模式或诊断信息选择下一项实验；独立验证器验收，控制器比较收益，模型最多进行有限轮修正。可先增加 execution_profile/expected_runs 作为真实前置问题，但只有在实现了相关执行路径后才把它计入功能。

保留固定模板无模型基线，比较它与带 Skill 的模型在决策成功率、工具调用数、总完成耗时上的差异。如果收益不明显，应把产品准确定位为“受限决策与验收工作台”，而不是通用自主 GPU 代码优化器。

### R11：现有 5/8 → 8/8 不能区分官方 Skill 与自研 Skill 的贡献

**证据：** `evidence/agent-eval/` 和项目报告第 7 页。当前比较的是无 Skills 与官方+四个自研 Skills，8 个固定策略任务、共 16 次生成。报告诚实注明平均输入 157.2 → 3152.2 tokens、单次贪心、任务与技能接近、不是 GPU 端到端成功率。

**修改：** 至少补无 Skills、仅官方 Skill、官方+自研 Skill；资源允许时加入仅自研 Skill 和固定规则基线。把业务策略评分与真实执行成功分开。新题采用未见措辞、不同数据分布、缺失参数与负向请求，并冻结期望输出。不要只在确定性贪心下对完全相同文本重跑几次就称为独立泛化证据。

**验收：** 表格同时给任务数量/通过数、错误采用数、模型 token、工具次数和端到端耗时；各条件使用相同验证器。任何收益不明显的结果照实保留。

### R12：复用目录需要隔离，manifest 完整性检查需要覆盖实际执行集合

**证据：** `scripts/replay_workflow.py:8–15` 固定解压到 `STATE/reused-workflow`，不清空目录，解压后只逐个检查 manifest 列出的文件，不检查实际目录是否存在未列出或上次遗留的代码。

**修改：** 每次使用新的临时目录，验证归档路径、成员类型、manifest 路径范围和精确成员集合后再运行。拒绝额外可执行代码/导入阴影文件；明确 manifest 自带哈希证明的是内容一致性，不自动证明来源可信。该项目仅接受团队受信任包时，仍需防止无恶意的旧文件污染。

**验收：** 连续复用两个不同版本不会混入旧文件；额外代码文件、路径越界、符号链接等按已定义策略拒绝；只使用清单中的运行快照。

## 报告书、文章、视频与前端展示

### 报告书：结构保留，补项目证据图与实际决策

9 页 PDF 没有明显溢出/截断问题，四配置表可读，性能口径明确。主要问题是内容几乎全是短段落与浅色表格，多页下半页留白明显，而没有系统架构、实际交互和失败样例的图片。不是需要更花哨的模板，而是需要读者能够快速看到系统怎样工作。

建议第 2 页补一张架构/数据流图；第 3 页放“10 vs 5”错误案例；第 4 页展示一次真实策略修复及对应 attempt；第 5 页保留暖态四配置表，并将新进程观测单独成小表；第 6 页展示后端建议在执行命令中的落地；第 7 页补 Skill 消融与成本；第 8 页补经验证的干净环境复现；第 9 页放团队、版本和最终项目入口。

封面的 12.40× 保留明确的“RTX 4090 / 500 万行 / 预热后同构 CPU 对照”范围，不让细小脚注承担所有限制条件。

删除或改写“用户提供的方案”“用户选择暂不公开”“本次实施”等开发代办视角。例如可写：“本项目面向固定结构的推理请求日志，采用受限迁移策略与独立验收流程。”AI 辅助设计或实现的归属可集中在致谢/工具使用说明中如实交代，不需要每节都使用“用户”作为项目作者之外的人。

“用户选择暂不公开”只来自材料中的表述，本次未另行验证该选择；不能据此替用户发布，也不应把它写成一项已获确认的外部事实。

### 文章：从功能介绍改为真实的工程取舍

现有文章准确但接近报告摘要，7 个短节、2 页且没有图。可围绕三个已有证据的转折扩写：为什么填零会导致结果错误；为什么 12.40× 不足以推荐一次性 GPU 任务；为什么通过验证的策略还需要与最终 ZIP 绑定。

修复本次 R01/R02 后，最后一个问题可成为很有价值的真实开发经历。但修复尚未完成前不能写成“已经解决”。配策略差异、错误值对照、暖态/新进程两种计时与导出实际执行截图。篇幅以征文规范为准，不把此前方案中的建议字数当作官方硬性要求。

### 视频：长度达标，但真实交互占比偏低

独立 ffprobe 得到 3:52.74，1920×1080，符合截图中的五分钟以内要求。视频明确区分历史记录、故障注入和合成旁白，应保留这些透明标识。

`project/media/source/narration/scenes.json` 显示 8 个段落中 1 段来自 WebM 实录，其余 7 段使用 PNG；`project/media/video-build.json` 给该实录段长度 28.6 秒。它不是假演示，但更像以真实结果截图为主体的说明视频。代表性画面中的修复段仍显示固定模板 diff，没有直观放大这次修复的具体字段与错误值。

建议保留开头定位和历史长任务结果，重录关键交互：点开失败项看到 10 vs 5；查看修复前后策略；选择一次性/常驻模式并看到不同的执行建议；导出 CPU 案例并实际 CPU-only 执行；最后用第二份数据验证复用。长 GPU 等待可以剪辑并标注，同一 run_id 保持可追踪。比增加一段概念讲解更有帮助。

### 前端：无需换框架，扩大证据区域

当前浅色工作台、失败/无收益状态、四配置图和离线标识可以保留。实际浏览器渲染中，代码区只露出约 5–6 行头部 diff，而页面下方存在较多可利用空间；建议增加“展开候选”模式，代码/策略区至少能看完整的关键聚合与修复内容。

检查详情不要先给整段巨大 JSON。第一屏给出 case、字段、参考值、候选值、差异原因和是否阻止发布，再提供原始 JSON 下载。把“审计模板差异”“本次策略差异”“第几次修复”作为不同标签。

将“结果一致性”“当前运行模式下的推荐后端”和“性能测量值”分开显示，避免绿色 VERIFIED_GAIN 被理解成任何运行方式都应采用 GPU。以上是交互与数据呈现修改，不要求从原生 JS 重写成 React。

## 修改顺序

第一轮先完成 R01 候选绑定、R02 后端遵从、R03 运行模式决策和 R04 交付包自洽，并补无 GPU 可运行的门禁/打包测试。第二轮处理 R05–R08 的终态、恢复、活动任务和历史快照。第三轮根据时间修 R09–R11，增加一条真正体现 Agent 决策价值的场景，而不是扩大技能数量。R12 的临时目录与清单校验建议随导出重构一起完成。最后再更新报告、文章、视频和哈希清单。

所有改动后的运行结果须对应新的代码/候选版本；不能沿用旧通过状态为新实现背书。旧运行可以保留作历史证据，须清晰标记版本。

## 最终验收门槛

| 验收项 | 通过条件 |
| --- | --- |
| 候选变更 | 验证后改策略被导出门禁拒绝 |
| CPU 建议 | KEEP_CPU 的日常 run 不触发 GPU |
| 运行口径 | one-shot / persistent-batch 的 UI、manifest 与实际执行一致 |
| 打包 | 包内 README 的每条入口在干净目录存在且可运行 |
| 任务结束 | 收尾未完成不发送终态，后续失败可被 UI 收到 |
| 重启恢复 | 不留下无法监管/取消的无限 RUNNING |
| 活动任务 | 浏览其他页面不丢取消入口，不误操作旧 run |
| 历史证据 | 策略、模板、测试、报告和 ZIP 对应同一版本 |
| 技能入口 | 导出 Skill 不启动新的迁移实验 |
| 复用隔离 | 不导入清单外或旧目录遗留代码 |
| 评测边界 | 不把 JSON 任务通过率写成端到端优化成功率 |
| 提交入口 | 源码/报告、视频、文章有评委可访问的真实地址；当前仅本地并不等于已提交 |

当前截图要求提交网址，而该包只包含本地材料。公开托管和权限检查是最后的交付动作；本次审查没有进行发布、上传或提交。是否必须使用 DGX Spark，应另据完整官方规则确认，不能仅凭培训主题断定当前 RTX 4090 成果不合规。

**最终建议：保持项目方向与受限模板，先修验证—导出—执行的一致性，再提高 Agent 的实际选择价值，最后优化演示。不要在定版前临时扩成任意代码生成与执行平台。**
